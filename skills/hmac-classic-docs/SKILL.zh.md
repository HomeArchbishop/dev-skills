# 经典文档

写清读者需要据此自行判断的事实。下面每条规则都用这个标准筛选：要求「必须有某个章节」的规则不属于这里，帮助读者理解行为和边界的规则才属于。

## 适用范围

- 这份 skill 约束的是怎么写，不是要不要写。除非用户要求做文档工作，否则不要创建或修改文档文件。
- 注释写用途、不显然的限制，或无法从局部代码看出的行为。不要逐行叙述实现。
  - 函数名为 `parseConfig` 时，注释「解析配置」没有价值；「只读取启动时的配置，运行期间不重新加载」有价值。

## 语言与术语

- 文档用中文写。
- 用普通的词，不要生造简称。
- 当中文不如英文精确时用英文术语，例如用 agent 而不是「代理」。
- 每个概念只用一个名字，并且一直用这个名字：首次出现用全名，之后用同一个名字。不要上一句写「输出端口」、下一句写「口」。页面里有术语表时，术语定义写在术语表里。
- 不要生造术语、缩写或比喻。一个词如果既不出现在代码里，也不出现在日常的中文技术写作里，就用平实的话把这个东西描述出来。

## 句子

按有经验的中文工程师向同事解释系统的写法来写。遵循中文的自然语序，不要把英文句子结构逐词搬过来。

- 写完整、无歧义的陈述。在操作步骤里，只要执行者是清楚的，省略主语没有问题。不要为了简短而省掉理解这句话所需的动作、对象或条件。
  - 「把请求转发给下一个服务」，不要写「往下推」。
  - 「通过请求里的标识找到对应的资源」，不要写「按标识找」。
- 用具体的动词。单字抽象动词「对」「收」「开」「走」「打」单独出现时没有意义。
  - 「两个服务报告的地址不一致」，不要写「地址对不上」。
  - 「创建一条连接」，不要写「开条连接」。
  - 「直接调用这个函数」，不要写「打这个函数」。
- 承载条件或结果的连接词要保留。不要为了把句子改短而删掉它。
- 写完整的叙述。不要用断句或压缩的标签代替一个句子：简洁去掉的是多余的信息，不是必要的词。
- 给出操作步骤时对读者说话，但不要把系统的行为写成读者可以做的事。
  - 「客户端在超时后取消请求」，不要写「你可以在超时后取消请求」。
- 避免翻译腔，例如「进行了一次……的处理」「被……所……」「对于……而言」「不是……而是」。直接写出执行者和动作。
- 不要在句子中间用破折号插一句补充。把它拆成两句。

## 介词

介词用双音节，或者写成与方位词成对的框架。单音节的「在」「用」「按」「对」不单独带宾语。

- 「位于 `src/domains/yearly/yearlyItems.ts`」，不要写「在 `src/domains/yearly/yearlyItems.ts`」。
- 「图片放在 `public/products/` 里」，不要写「图片放在 `public/products/`」，也不要写「图片在 `public/products/`」。
- 「使用 `rem` 布局」，不要写「用 `rem` 布局」。
- 「按照路径设置缓存」，不要写「按路径设置缓存」。

方位词是框架的一部分，不要省略：「放在……里」「写在……里」「登记到……里」。

- 只说东西在哪里的句子没有说出要做什么。改成写出动作的句子。
  - 「修改产品只用改 `src/domains/product/productItems.ts`」，不要写「数据在 `src/domains/product/productItems.ts`」。

## 标题

- 标题标定一个确定的主题：一个概念、一个 API、一项操作、一种行为，或它们之间的关系。
- 使用主题既有的名字，标题和正文里用同一个名字。
- 标题的范围要与这一节相称：既不超出这一节所讲的内容，也不要窄到一个没有独立主题的细节。能直接命名主题时，不要留下空泛的标题。
- 标题用主题名，不要用问句、操作指令、结论，或引出下文的句子。
- 让标题负责定位，让第一段说明行为。不要把整句话压进标题里。

## 说明

说明系统做什么、在什么时候做、为什么这样做，只写到读者能作出正确判断为止。

- 从读者需要理解的行为或概念开始写。只有当背景有助于说明这个行为时，才介绍背景。
- 把关系写明确：什么触发一个动作、它改变了什么、它返回什么、在哪些条件下。只写这一段用得上的关系。
- 通过可观察的行为来说明概念。一个说法没有例子就很难理解时，用一个小而真实的例子，并说明它展示的是什么。
- 写出默认值、限制、失败情况，以及影响读者使用或修改这个系统的区别。
- 详细程度与主题相称。一条代码注释可能只需要一句话；一个不熟悉的概念可能需要几段。
- 让主题决定结构。不要求每个页面或每一节都按照同一套提纲来写。

## 不写什么

- 不要称赞设计，不要声称某个选择是有意为之，也不要告诉读者这些内容很容易。
- 不要写修辞句或拟人句。
  - 「返回 `invalid_input`，这次请求不会开始」，不要写「不会猜着往下跑」。
  - 「无法恢复的任务直接记为失败」，不要写「老实失败，不会假装还在跑」。
  - 「无法转换成 JSON 的对象会报 `payload_invalid`」，不要写「不会偷偷转成字符串」。
- 不要留下编辑痕迹：不要写中间推理，不要写变更历史，不要写重复代码已经说过的内容的句子。重构之后写「业务逻辑在 `ctx.runs` 里」，这是编辑痕迹。
- 不要用凑数的开头，也不要评论文本本身。不需要引言时，直接从主语开始写。
- 不要把一个句子拆到几条列表项或几行表格里。每一条都是一个完整的陈述。
